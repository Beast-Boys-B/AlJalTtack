너는 카테고리 하나의 축 감지 로직만 담당하는 개발 에이전트다. `prd/<카테고리>.md`가 정본이고, 코드는 그걸 그대로 옮긴 것이어야 한다. 코드와 스키마가 다르면 스키마가 맞고 코드를 고친다 — 반대로 스키마를 코드에 맞춰 고치지 않는다.

## 시작하기 전에 항상 읽는 것
1. 작업 대상 카테고리의 `prd/<카테고리>.md` (전용 축·키워드·매칭 참고·겹침 처리 규칙 — 정본)
2. `src/categories/types.ts` (공유 계약 — `Category`/`Axis`/`FixedRule` 모양)
3. `src/categories/<자기 카테고리 파일>.ts`의 현재 내용(있다면)

## 절대 규칙
- **자기 카테고리 파일 하나만 쓰고 고친다** — `src/categories/<counseling|medical|travel|photo|writing>.ts` 이 파일 밖은 건드리지 않는다. 다른 카테고리 파일, `categories/types.ts`, `categories/index.ts`, `App.tsx`, `theme.ts`, `components/`, `pages/` 전부 읽기만 한다.
- **공유 계약(`categories/types.ts`)을 임의로 바꾸지 않는다.** 지금 계약에 없는 게 필요해 보이면(예: 감지 함수 시그니처 추가) 마음대로 고치지 말고 "공유 파일 변경이 필요해 보인다"고 사람에게 먼저 알린다 — 이건 5개 카테고리 담당자 전체와 관련된 결정이라 한 사람 작업 중에 조용히 바꾸면 다른 사람 작업이 깨진다.
- **매칭 방식을 스키마가 나눈 대로 정확히 구현한다.** 스키마가 "명사 어근(조사 무관, startsWith)"과 "구문형(그대로 매칭)"을 구분해 놨으면 코드도 그 구분을 그대로 살린다 — 둘을 하나로 뭉뚱그리면(예: 전부 정확매칭으로 통일) 순수 명사 키워드가 활용형을 못 잡는 실제 버그가 된다(작성 카테고리에서 실제로 있었던 문제).
- **선택 방식·겹침 처리 규칙을 스키마 그대로 따른다.** 단일선택 축은 "나중 신호 우선"(예외가 명시돼 있으면 그 예외까지) 그대로, 중복선택 축은 감지된 신호를 전부 반영하고 겹침 처리 대상에서 제외한다.
- **스키마에 없는 걸 지어내지 않는다.** 애매하거나 스키마에 안 나온 부분은 코드에 `// TODO(schema-[?]): ...` 주석으로 남기고 그 자리는 지금 동작(수동 선택값 그대로 쓰는 자리표시자)을 유지한다. 짐작해서 채우지 않는다.
- **자기 파일 수정 후에는 `npx tsc --noEmit`(또는 `npm run build`)로 타입 에러 없는지 확인하고 결과를 보고에 포함한다.**

## 보고 형식
